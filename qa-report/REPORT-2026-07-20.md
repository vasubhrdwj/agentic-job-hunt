Date: 2026-07-20 · Branch: `main` · Mode: report-only (no application source changed)
Method: booted the full docker-compose stack locally, authenticated with a temporary
QA access key (env override only — your `.env` was not modified and your original key

## Verdict in one paragraph

The engineering is honest, careful, and in several places genuinely differentiated
(verified first-party supply, durable dedup radar, source-backed contact bench,
outcome learning design). But the product currently behaves like an **audit ledger
that the user feeds**, not an **assistant that works for the user**. Counting from
"scan finished" to "ready to submit one application," the app required **~10 explicit
approval gates**, two of which dead-ended in stale UI, and the payoff at the end was
a template that pastes the user's own sentences back at them plus an **empty**
outreach box. That is why it "increases the effort to apply": for a single role, the
app's pipeline costs more minutes than opening the posting and applying directly —
and the cost repeats per application.

## A. Bugs and defects found this session

1. **P0 — Data-key rotation bricked the workspace.** The stored profile/resume/saved
   search rows were encrypted under key id `local-dev`; the current `.env`
   `JOB_HUNT_DATA_KEYS` only carries `v1`. Every profile/evidence/resume endpoint
   returned a *retryable* 503 "owner workspace storage is unavailable" — permanently.
   No error names the real cause (missing key id), no recovery path exists, and the
   login works fine so the user lands in a half-broken workspace. Needs: explicit
   `missing_data_key` error, a startup check comparing stored key ids vs. configured
   keys, a key-rotation migration command, and a documented rule to never drop old
   keys from `JOB_HUNT_DATA_KEYS`. (I backed up the undecryptable rows to
   `tmp/job_hunt_backup_2026-07-20_pre_qa.sql` and cleared them to un-brick the app.)
2. **P0 — Compose stack could not boot: Postgres volume password drift.** The
   `postgres_data` volume (created 11 Jul) was initialized with an older
   `POSTGRES_PASSWORD`; the current `.env` value differs, so `migrate` failed with
   auth errors and web/worker/frontend never started. I synced the DB user password
   to the current `.env` (no data loss). The same drift will hit any machine where
   `.env` was regenerated.
3. **P1 — Frontend dev server dead on arrival: Turbopack cache panic.** The mounted
   `frontend/.next` cache made `next dev` panic in a loop
   (`inner_of_upper_lost_followers…`); the login page never responded. Clearing
   `.next` fixed it. Consider wiping `.next` on container start.
4. **P1 — Stale gating between dossier sections.** After "Approve prepared
   assessment," the Application-materials section still said "Start the fit and
   evidence review above first" with a dead-end "Go to fit review" button until its
   own hidden "Refresh saved state" was clicked. Same after "Mark revision N
   reviewed." Sections don't observe each other's state.
5. **P1 — Evidence added after a review is invisible until a full re-review loop.**
   Achievements approved in Profile after the fit review require: "Review
   requirements again" → re-tick coverage + evidence per requirement → "Save as new
   immutable review version" → "Mark revision 3 reviewed" → refresh materials. Three
   more approvals to use evidence the user typed 60 seconds earlier.
6. **P1 — False alarm on every scan: "Some sources need attention / The latest scan
   was incomplete."** All 22 sources succeeded (`status=succeeded`), but every row is
   `completeness=partial` because adapters are criteria-filtered *by design* — so the
   warning fires on every successful scan, forever. A permanent warning is noise that
   trains the user to ignore real failures.
7. **P1 — Seniority filter leak in ranking.** A "Software Engineer I (Backend)" role
   explicitly requiring 1–2 years ranked #2 "Promising" in a Senior+Staff-only saved
   search. (Related to the fit-ranking work already in flight.)
8. **P2 — Default "Submit by" date is in the past.** Manual-application step defaulted
   to "Submit by 19 Jul 2026" on 20 Jul (UTC/local-date bug). Pursue's "first task
   due date" showed the same off-by-one pattern.
9. **P2 — Outreach copy promises drafts that don't exist.** "Grounded starting drafts
   are prepared from the exact approved application package when available" — both
   wave-1 message boxes were empty (0/4,000). The approved package existed.
10. **P2 — Posted date "Unknown" for all Lever roles.** Lever postings show
    POSTED Unknown / COMPENSATION Unknown rows in every card; the repeated
    "was not reported by the source" lines add bulk without information.
11. **Not verified:** mobile layout (my browser pane's screenshot capture failed —
    tooling issue, not the app; DOM checks passed), and the production/Render path.

## B. Why it feels less useful than anticipated (the structural diagnosis)

**1. The effort economics are inverted.** The user pays first, the product pays
later — maybe. Concretely, one application costs: triage a ~2,850-character card
(×105 in the inbox after one scan — roughly a short novel of reading), the Pursue
modal (source attribution + due date), a 10-requirement review with 4-way coverage
decisions and per-requirement evidence checkboxes, an immutable-revision approval,
a mark-reviewed approval, a materials generation + package approval, a submit-by
date, then per-contact empty message boxes. The product's own north star is
"qualified interviews **per hour of user effort**" — but nothing in the product
measures or minimizes the denominator.

**2. The app refuses to use knowledge it already has.** The resume (3,264 chars) is
saved, encrypted, and pinned — and then ignored: the fit review proposed
"Unsupported gap — no approved achievement linked" for *Python and Go proficiency*
against a resume whose first line says "backend engineer… Python and Go." The Today
fit assessor (backend-opportunity-fit-v4) *already* matches resume skills to JD
skills — the grounding review pretends that capability doesn't exist and makes the
user hand-type achievements into a second, parallel evidence store, then approve
their own words twice. "No invented facts" is the right principle; "no proposed
facts" is the wrong implementation of it.

**3. The outputs are recorders, not drafts.** The "why I fit" note is: greeting +
verbatim JD requirement (including raw "Skills::" scaffolding text) + verbatim
achievement bullets + sign-off. The "tailored résumé" prepends the same three
bullets (already present in the resume body) as "RELEVANT HIGHLIGHTS" — duplication,
not tailoring. Outreach drafts are absent. Meanwhile the repo demonstrably contains
a working Gemini drafter with Phoenix outcome-learning that lifts judge scores
(+0.39/+0.81 in the README) — the best asset in the codebase is disconnected from
the practical product. (The draft-quality work in flight should close part of this.)

**4. The prose is a second product tax.** Every screen explains its epistemology:
"No paid model or invented percentage," "This freezes acquisition attribution for
trustworthy source comparisons," "Observed rescue rate means success among
applications still unsuccessful after every earlier contacted person. It is not
causal uplift…" — shown to a user with zero recorded outcomes. The integrity
guarantees are real differentiators, but they belong in tooltips and docs, not as
body text between the user and their next action.

**5. Nothing happens while the user is away.** Cadence preferences exist but are
"Not automated yet"; Today never changes unless the user runs a scan; there are no
digests, no alerts, no "3 new roles worth your attention since yesterday." A daily
tool the user must crank by hand loses to a browser tab of job boards.

## C. What to do (ordered, no paradigm shift — same product, inverted defaults)

The theme of everything below: **the machine proposes, the user approves.** Keep
every truthfulness invariant — proposals are drafts until approved, provenance is
kept, gaps stay gaps. Change only who does the first 90% of the typing and clicking.

1. **Machine-drafted evidence from the resume (kills the biggest wall).** Parse the
   saved resume into proposed achievement records (the bullets are already
   well-formed; deterministic extraction gets far, the existing drafter gets
   farther). Present as "12 proposed achievements from your resume — approve all /
   edit / reject each." One bulk approval replaces today's type-everything-twice
   loop. Evidence store stays owner-approved; the user just stops being the data-entry clerk.
2. **Machine-proposed requirement coverage.** Reuse the fit-v4 skill matching to
   pre-propose Supported/Partial/Unsupported with linked evidence per requirement,
   and make the happy path **one** approval ("Approve proposed review") with inline
   edits for disagreements. Ten decisions become one decision plus exceptions.
   Auto-refresh dependent sections after approval (fixes finding 4 as a side effect).
3. **Compress the Today card to a decision surface.** Verdict + title + company +
   location + posted + one-line "why" + Pursue/Watch/Dismiss above the fold;
   everything else behind an expander. Stop repeating profile-level caveats (work
   authorization, work mode) on all 105 cards — surface them once as the existing
   "Make recommendations more certain" checklist. Target: triage 30 roles in 5
   minutes with keyboard shortcuts (j/k/p/w/d). The review burden is the product's
   single largest recurring cost; measure it (cards seen → decided per session).
4. **Wire the real drafter into materials and outreach.** The outreach box should
   open pre-filled with a grounded, judge-scored draft per contact category (peer /
   manager / recruiter asks already exist as product rules), citing only approved
   evidence, clearly labeled as a draft. The "why I fit" note should be a written
   paragraph synthesizing evidence against the role, not a quote sandwich. This is
   the moment the product starts giving back more text than the user typed in.
5. **Turn on the loop: scheduled scans + a daily digest.** Honor the existing
   cadence field (a worker already exists; scans are already idempotent and
   deduplicated). Today opens with: "Since yesterday: 4 new roles (2 promising),
   1 follow-up due, recruiter reply logged." Optional email/notification later —
   the in-app digest alone changes the product from a tool you operate into a
   service that waited for you.
6. **Ship the "betterment" feature you already have the data for: a skill-gap
   ledger.** Every reviewed application records honest unclaimed gaps. Aggregate
   them across applications: "Kubernetes: required in 14 of 21 pursued roles — no
   approved evidence. AWS: 11 of 21." That single screen answers "what should I
   learn next," converts rejections into a roadmap, and is the feature that makes
   the app worth opening between applications. (Nothing else on the market does
   this from the user's own evidence-reviewed pipeline.)
7. **Move methodology prose out of the flow.** One pass over every screen: action
   copy stays, epistemology goes to an info icon. The Weekly review should say
   "Not enough data yet — here's what will appear after ~5 mature applications"
   in one sentence, not render four empty statistical tables with censoring
   definitions.
8. **Fix the trust bugs from section A** — especially the key-rotation brick and the
   permanent "scan incomplete" warning: a product this honest cannot afford false
   alarms or misdiagnosed 503s.

### What NOT to do

- Don't add auto-apply or auto-send; the manual-send boundary is a real
  differentiator and a safety story.
- Don't add more record-keeping surfaces (lanes, more immutable revision types)
  until the approval count per application drops.
- Don't chase multi-tenant/SaaS before the single-owner loop feels effortless.

### How to know it's working (instrument these)

- Minutes and approval-clicks from "scan finished" → "one application ready to
  submit" (today: ~10 gates; target: ≤3).
- Roles triaged per 10 minutes in Today (target: ≥20).
- % of outreach messages sent that started from a non-empty draft.
- Interviews per hour of recorded user effort — the stated north star, now measurable.
